## Human interaction and limits

- Give one coherent check at a time with **two to four short actions**, the exact control/song to use, and what result to report. Prefer a short response such as “works / value unchanged / wrong sound / crash,” with a follow-up only when needed. Batch checks that share the same song, permission or audio route.
- Ask for text observations. Do not request or inspect screenshots, photos, recordings or videos. Human observation is the evidence for appearance, audible artifacts and tactile usability; do not claim personal visual/listening verification from source code.
- Start with `500 Miles` by the Proclaimers. Use another requested real-catalog song only for a demonstrated missing behavior, such as a different mode or chord-only passage. Verify the relevant musical property first. Do not require the human to sing accurately across an excessive range or force an uncomfortable pitch.
- Aim for **five active testing minutes per case**, up to **ten for microphone/recovery**, with no more than **two reproduction attempts** for the same issue. Exclude waiting for a human response from active test time, but silence is never a pass. After the bound, record FAIL, BLOCKED or INCONCLUSIVE and move on.
- If hardware, account access, an accessory or an OS event is unavailable, mark that case BLOCKED and continue other cases. Do not require purchasing equipment, sharing credentials, changing accounts or resetting a personal phone to complete the matrix.
- Keep only one simulator booted. Do not create new runtimes/devices for this pass. Supported iPad/small-device cases can be recorded as blocked if no suitable environment is available.
- Preserve personal catalog/user data. Destructive clean-install, permission reset, disk-full and catalog-corruption scenarios belong to isolated automated stores or require an explicitly chosen disposable device/container. A human's everyday phone is not disposable test data.
- On a crash, collect build, triggering action and available text crash/console evidence before repeating. After a known reproduction, avoid further identical crashes. Missing feedback or incomplete evidence must remain unresolved.

## Special handling for physical recording/DSP evidence

Read Prompt 1's configured DSP baseline and its actual results if available. Standard analysis is 16 kHz mono, 2,048/512 samples; fast melody tracking is 1,024/256. Synthetic parity of YIN, gates, smoothing and freshness does not establish hardware capture parity.

For physical evidence, record input/output route, relevant OS permission, selected tracking mode, reported native format/conversion diagnostics if available, and whether failures occur only with speaker playback or particular accessories. Use existing text diagnostics rather than building a broad new instrumentation system. A phone's native capture rate need not itself be 16 kHz if conversion produces the required analysis stream.

A known source tone can support a numeric frequency/cents comparison; ordinary singing supports usability and plausibility observations. Do not infer DSP failure from a human's unmeasured pitch, nor infer DSP success from hearing approximately the right note. Keep acoustic leakage, preprocessing, route latency, algorithm output and UI latency as separate findings. If a needed measurement/source is unavailable, mark that measurement BLOCKED and preserve the qualitative observations.
